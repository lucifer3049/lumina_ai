## 5. 可行度總結（1 人 + AI 視角）

**成立的理由**：工作包粒度小且有 DoD、驗收測試先行 + smoke + 任務卡把 AI 的失控面積壓到最小、Django Admin 紅利省掉整個後台前端、裁切原則明確（介面可後補、機制不可後補）。

**最大的三個現實風險**（非設計問題）：R4 單人瓶頸（13 已上調為高/高）；29 週是馬拉松，節奏管理比技術更可能是成敗因；文件紀律本身——每次「實作偏離文件」若不即時回寫，這套體系半年後就會腐化為裝飾品。第三點的解法已內建（CLAUDE.md 的停下回報規則），但執行靠人。

**建議的下一步順序**：~~F-01~~ ✅ → ~~F-02/F-03~~ ✅ → ~~F-04–F-10~~ ✅（**P1/P2 全數結案，文件階段無遺留項**）→ Phase 0 開工 → ADR-001 spike 報告出爐後回頭更新 01 與本報告分數；Phase 2 golden set 驗證 F-07/F-08 的實測項。

## 8. Phase 0 結案程式審查（2026-08-07）

§1–7 審的是**計畫書**；本節審的是 Phase 0 交付的**程式碼**，因此編號用 `C-xx` 與 `F-xx` 區隔。依 §7 的 living document 約定，每個 Phase 結束時做一次。

審查方式：8 個獨立角度各自產出候選（逐行掃描、移除行為稽核、跨檔契約追蹤、重複、簡化、效率、抽象層次、CLAUDE.md 規範），去重後逐條驗證真偽。**13 條當次修掉**（5xx 錯誤 detail 外洩且不記 log、遮罩對 JSON 字串／Bearer JWT／URL 內嵌憑證的三處漏接、遮罩對 namedtuple 會把請求打成 500、巢狀交易換租戶、短路 400 無存取記錄、image 跑 dev 設定且破壞日誌契約、seed 非原子產生假基準線、診斷端點洩漏 DB 拓撲、壓測腳本無 timeout、`DISABLE_SERVER_SIDE_CURSORS`、codegen 守門空轉、`details` 帶 UUID 使 4xx 降級成 500、死碼與誤導 docstring）。

| C-14 | `config/logging.py` 的 `_StdoutHandler` 用 property + no-op setter 覆寫 `stream`（吞掉 `StreamHandler.__init__` 的賦值）；而 `tests/api/test_request_logging.py` 的 fixture 註解寫「handler 綁的是當下的 `sys.stdout`」——兩處對綁定時機的敘述相反，下一個查「log 不見了」的人會採信錯的那份 |
| C-15 | `core/db.py` 的 `orm_runtime_knobs()` 回報的是**設定值**而非 executor 實際的 `max_workers`，而該端點存在的理由正是抓「設定沒生效」。目前兩者一致（executor 在 import 期由同一個 setting 建立），改成延遲建立或可替換時這條就要動——已在該函式 docstring 標明 |
| C-16 | `config/settings/dev.py` 重複宣告 `DEBUG = False`（`base.py` 已有）。同一旗標兩處宣告，改了其中一處會得到「設定沒載入」的誤判 |
| C-17 | `tests/integration/test_infra_object_storage.py` 有 8 處 `# type: ignore[no-untyped-def]`（理由是 boto3 無公開型別）。而 `boto3.*` 已在 `pyproject.toml` 設 `ignore_missing_imports`，標 `Any` 即可通過——整條抑制會讓 fixture 回傳型別與每個消費端參數都不受檢查，且這個寫法一旦被複製進產品程式就會遮掉真正的簽章錯誤（CLAUDE.md：型別註記必寫） |
| C-18 | `frontend/src/api/client.ts` 的空 body 判斷寫兩次：`status === 204 \|\| Content-Length === '0'` 的守門被下一行的 `text ? JSON.parse(text) : null` 完全涵蓋，且後者還多蓋 chunked 空 body 與 205 |
| C-19 | `apps/spike/management/commands/seed_spike.py` 直接用 `SpikeItem.objects` 而非 `TenantScopedRepository`（鐵則 4）。唯一豁免依據是 `core/uow.py` docstring 的「Migration 與維運腳本走 bypass 角色」——豁免寫在**另一個模組**裡，而同樣形狀複製進 Phase 1 的 Celery task 就是無守門的跨租戶操作。1A 的角色拆分（C-01）落地時一併把豁免寫成明文 |

小結：19 條未處理項裡沒有一條是當前的安全或正確性風險——8.1 的兩條是**未來**會靜默失效而已排入 Roadmap，8.3 需要可信量測才動得有意義，8.4 全屬維護成本。與 §6 的模式觀察一致：程式碼的漂移形狀也是「改了 A 忘了同步 B」（C-11 / C-13 / C-14 / C-15 全是同一份事實存在兩處）。
