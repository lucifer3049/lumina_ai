## 1. 專案概述

### 1.1 目標

建立一套 Production Ready 的 Enterprise AI Knowledge Platform（AI 智庫平台），支援 Multi-tenant SaaS 營運模式，核心能力包含：

- LLM Chat（SSE Streaming、Multi-turn Memory）
- Knowledge Base 與 Document 管理
- RAG Pipeline（Hybrid Search、Reranking、Context Compression、Citation）
- Tool Calling（Tool Registry、Permission、Lifecycle）
- ETL Pipeline（PDF / Word / Excel / CSV / JSON / API / Database / Website）
- Prompt Management（版本化、測試、快取）
- AI Model Management（多 Provider、Model Routing、Fallback）
- Evaluation、Monitoring、Audit Log、Usage / Cost Tracking

### 1.2 技術架構摘要

| 層級 | 技術選型 |
|------|----------|
| Backend ORM | Django + Django ORM |
| API Layer | FastAPI（REST、OpenAPI、SSE Streaming、AI Gateway） |
| Frontend | Vue 3 + TypeScript + Pinia + Vue Router |
| Database | PostgreSQL |
| Vector DB | pgvector |
| Cache | Redis |
| Background Job | Celery |
| Storage | MinIO |
| Deployment | Docker Compose（保留 Kubernetes / Kafka / Microservices 升級路徑） |

### 1.3 架構風格

**Modular Monolith + Clean Architecture + DDD**，明確區分 Domain / Application / Infrastructure / Interface Layer，保留未來拆分 Microservices 的能力，同時遵循 YAGNI 避免過度設計。

## 3. 原始提示詞遺漏補充分析（Gap Analysis）

原始提示詞已相當完整，以下為經審視後認定**遺漏或未明確定義**的項目。各項目已排入對應文件補齊，優先級標準：P0 = 不解決無法開工、P1 = MVP 前必須定案、P2 = 上線前補齊。

### 3.1 架構層（P0）

| # | 遺漏項目 | 說明 | 補齊位置 |
|---|----------|------|----------|
| G-01 | **Django 與 FastAPI 共存邊界** | 原提示詞同時指定 Django ORM 與 FastAPI，但未定義兩者如何共存：Django ORM 在 FastAPI async context 的使用策略（sync ORM in threadpool vs. asgiref）、DB connection 生命週期、由誰負責 Migration、Django Admin 是否啟用。這是本案最大的架構風險，必須以 ADR 形式定案。 | 01 |
| G-02 | **Multi-tenant 隔離模式選型** | 需求列出 Multi Tenant 但未指定隔離模式：Shared Schema + `tenant_id`（Row-Level）vs. Schema-per-Tenant vs. Database-per-Tenant。影響所有 Table 設計、pgvector 查詢、備份策略。 | 01、05 |
| G-03 | **LLM Provider 抽象層** | 提到 AI Gateway 與 Model Routing，但未明確要求 Provider Interface（OpenAI / Azure / Ollama / OpenRouter / Gemini 可切換）之設計，含 Streaming、Tool Calling、Embedding 三種能力的統一介面。 | 01、06 |
| G-04 | **技術版本與依賴管理規範** | 未定義 Python / Node / PostgreSQL / pgvector / Redis 版本、Python 依賴管理工具（uv / poetry）、lockfile 策略。 | 01 |

### 3.2 功能層（P1）

| # | 遺漏項目 | 說明 | 補齊位置 |
|---|----------|------|----------|
| G-05 | **Quota 管理與強制執行** | 有 Cost Tracking / Usage Statistics，但缺少租戶級 Quota Enforcement：Token Quota、Document 數量上限、Storage 上限、超額行為（阻擋 / 降級 / 計費）。SaaS 商業模式的必要條件。 | 04、10、12 |
| G-06 | **SSE 斷線與恢復機制** | 指定 SSE Streaming 但未定義：client 斷線時 token 計費歸屬、部分回應的 message 持久化、`Last-Event-ID` resume、Nginx/Traefik buffering 設定。 | 06、09 |
| G-07 | **通知系統（Notification）** | ETL 完成、Job 失敗、Quota 告警需通知使用者，未定義通知通道（in-app / email / webhook）與模組歸屬。 | 04 |
| G-08 | **全文檢索引擎選型** | Hybrid Search 的 keyword 端未指定實作：PostgreSQL FTS（含中文斷詞 zhparser/pgroonga）vs. 外部引擎。中文知識庫此項是檢索品質關鍵。 | 06 |
| G-09 | **檔案上傳治理** | 未定義上傳大小上限、MIME 白名單、惡意檔案掃描、重複檔案去重（content hash）。 | 08、10 |
| G-10 | **租戶生命週期管理** | Tenant onboarding / offboarding 流程、租戶資料匯出（可攜權）、租戶刪除時的級聯清理（DB、Vector、MinIO、Redis）。 | 04、05 |
| G-11 | **OpenAPI → TypeScript Client Codegen** | 前後端契約同步機制未定義，建議以 OpenAPI schema 自動產生前端 typed client，作為 Single Source of Truth。 | 03、09 |

### 3.3 治理與合規層（P1–P2）

| # | 遺漏項目 | 說明 | 補齊位置 |
|---|----------|------|----------|
| G-12 | **資料保留與隱私合規** | 對話 / 文件 / Audit Log 保留期限、個資法（台灣 PDPA）/ GDPR 刪除權、PII Masking 政策未定義。 | 10、12 |
| G-13 | **大表資料治理** | `messages`、`usage_logs`、`audit_logs` 為高成長表，未規劃 Partitioning（時間分區）、歸檔與清理 Job。 | 05 |
| G-14 | **Feature Flag 機制** | 多租戶 SaaS 逐租戶開關功能（如新模型、新檢索策略灰度發布）需要 Feature Flag，未提及。 | 04 |
| G-15 | **測試策略細化** | 列出測試層級但未定義：LLM Mock 策略（禁止測試呼叫真實 API）、RAG Evaluation Dataset 管理、pytest + factory_boy 慣例、CI 中的測試分層執行。 | 12 |
| G-16 | **風險登記冊與驗收標準** | Roadmap 有工作量估算，但缺專案風險管理（技術風險 / 資源風險 / 外部依賴風險）與各階段驗收標準（Definition of Done）。 | 13 |
| G-17 | **i18n 與多語策略** | 前端 UI 多語、知識庫內容語言偵測、Embedding 模型多語能力對照未定義。預設優先繁體中文＋英文。 | 03、06 |
| G-18 | **第三方依賴 License 審查** | 商用環境需審查依賴 License（GPL 污染風險）與 SBOM 產出。 | 12 |

### 3.4 本計畫書的處理原則

- P0 項目（G-01 ~ G-04）於 **Stage 1** 以 ADR（Architecture Decision Record）形式定案，因為後續所有文件都依賴這些決策。
- P1 / P2 項目納入對應章節文件，並反映到 Roadmap 的工作量估算中。
- 依 YAGNI 原則，以下項目**明確列為 Out of Scope（第一版不做）**：多區域部署（Multi-region）、SSO/SAML（保留 OAuth 介面）、行動 App、即時協作編輯、自訓練模型（Fine-tuning）。

## 4. 關鍵架構決策預告（Stage 1 定案）

下列決策已於 `01_系統架構總覽.md` 以 ADR 形式完整分析並定案（定案時擴充為 7 項：另含 ADR-007 技術版本與依賴管理，對應 G-04）；本表保留當時的傾向方案供決策軌跡回溯，實際內容以 01 為準：

| ADR | 決策點 | 傾向方案（理由詳見 Stage 1） |
|-----|--------|------------------------------|
| ADR-001 | Django 與 FastAPI 共存 | FastAPI 為唯一對外 API 入口；Django 僅作為 ORM / Migration / Admin 引擎，ORM 呼叫透過 threadpool 包裝進 async context；單一 codebase、單一部署單元 |
| ADR-002 | Multi-tenant 隔離 | Shared Schema + `tenant_id`（Row-Level），配合 Repository Layer 強制注入 tenant filter；未來大客戶可升級 Schema-per-Tenant |
| ADR-003 | Vector DB | pgvector（與主庫同居），HNSW index；文件量達百萬級再評估獨立 Vector DB |
| ADR-004 | 即時傳輸 | SSE（單向串流足夠，較 WebSocket 簡單且對 LB 友善），支援 reconnect + resume |
| ADR-005 | 訊息佇列 | Celery + Redis broker；事件量成長後升級 Kafka（介面先以 Event Publisher 抽象） |
| ADR-006 | Modular Monolith 模組邊界 | 以 DDD Bounded Context 切分：Identity / Knowledge / AI / Conversation / Tool / Platform，模組間僅透過 Service Interface 溝通 |
