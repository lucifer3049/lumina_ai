# Feature Specification: API Key 認證與管理（2C-3）

**Feature Branch**: `003-api-key`

**Created**: 2026-09-06

**Status**: Draft

**Input**: User description: "API Key 認證與管理（對齊 docs/plan/13 §4 的工作包 2C-3）。讓機器（系統整合、B2B 客戶）能以 API Key 呼叫本平台的 API，並讓租戶管理者能自助建立、檢視與撤銷這些 key。含建立/列出/撤銷（建立時一次性回明文）、能真的當認證用（第二種 principal）、scope 為 permission 子集、支援過期與即時撤銷、last_used_at 節流寫入、稽核要能指認 actor 是 api_key。不含前端畫面（歸 2C-5）、不含 per-key IP allowlist 與 HMAC request signing。"

## 背景（為什麼需要這個 Feature）

09 §1 的認證表從 Phase 0 起就有兩列：**JWT 給人、API Key 給機器**。第一列在 1A 做完了，
第二列到今天為止**一行程式碼都沒有**。

少了它，一個要接本平台的系統整合只剩一條路：**拿一個真人的帳號密碼去登入**。這條路上的每
一件事都是壞的，而且壞得很安靜——

- 那個整合拿到的權限是**那個人的全部權限**，不是它需要的那幾項。「最小權限」在這裡不是做
  不好，是根本沒有東西可以設。
- 要停掉那個整合，只能停掉那個人。整合與人的生命週期被綁在一起，而它們本來沒有關係。
- 每 15 分鐘要換一次 access token，於是整合必須長期持有密碼——**一個為互動式登入設計的憑證，
  被交給一個永遠不會登出的程式**。

**但最安靜的是第三件事**：稽核紀錄的「這是誰做的」從設計之初（05 §179）就有三種合法答案
——**使用者、API Key、系統**——而目前**沒有任何路徑寫得出第二種**。也就是說今天每一筆由
機器發起的動作，稽核上都記成**某個人做的**。那份稽核紀錄看起來完整、格式正確、每一列都
有 actor——而它對「誰做的」這個問題的回答是錯的。**錯的稽核比缺的稽核更難發現**：缺的那一
天會有人問「怎麼沒有紀錄」，錯的那一天不會有人問任何事。

還有一個已經成形的形狀限制值得先寫下來。10 §2.2 定義 key 的權限是 **scope——permission 的
子集、建立時指定**；而目前的權限判定吃的是**角色**。這兩者不是同一個東西：角色是「這個人
是什麼」，scope 是「這一把鑰匙准開哪幾扇門」。把 key 硬塞進角色模型，等於每一把 key 都必須
挑一個現成角色來扮演，而那正是本 Feature 要消滅的「整合拿到的權限等於某個人的全部權限」。

因此本 Feature 的核心不是三個 CRUD 端點，是**認證層第二種 principal 的成立**：一個沒有人、
沒有登入、沒有 refresh、權限由一份明確清單決定的呼叫者。CRUD 是它的管理介面，不是它本身。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 租戶管理者自己發得出一把鑰匙，也收得回來 (Priority: P1)

租戶的管理者要接一個外部系統。他自己在平台上建立一把 API Key、指定它能做哪些事、拿到明文
交給對方；哪天不需要了或懷疑外流了，他自己就能收回，不必找平台方、也不必動任何人的帳號。

**Why this priority**: 沒有發放與撤銷，key 這個東西在租戶手上不存在。這是整條路的第一步。

**Independent Test**: 以管理者身分建立一把 key、在清單上看到它、撤銷它、確認清單上的狀態
改變。完全不需要「用 key 呼叫」那一半。

**Acceptance Scenarios**:

1. **Given** 一位具備 API Key 管理權限的使用者，**When** 建立一把 key 並指定名稱與權限範圍，
   **Then** 系統回傳**完整明文一次**，且回應中明確表示這是唯一一次。
2. **Given** 該 key 已建立，**When** 再次列出或查詢它，**Then** 看得到足以辨識它的資訊
   （名稱、前綴、權限範圍、建立者、建立時間、到期時間、狀態），**但看不到明文，也看不到任何
   能還原明文的資料**。
3. **Given** 該 key 已建立，**When** 管理者撤銷它，**Then** 撤銷立即生效，且該動作留下稽核。
4. **Given** 一位不具備 API Key 管理權限的一般成員，**When** 嘗試建立、列出或撤銷 key，
   **Then** 被拒絕。
5. **Given** 另一個租戶的 key，**When** 本租戶的管理者列出或嘗試撤銷它，**Then** 看不到、
   也動不了。

### User Story 2 - 機器拿著那把鑰匙呼叫 API，而且只開得了被授權的那幾扇門 (Priority: P1)

外部系統帶著 key 呼叫平台的 API。它應該被當成一個合法的呼叫者、自動落在正確的租戶裡，而且
**只能做建立時指定的那幾件事**——即使發放它的那個人本身權限大得多。

**Why this priority**: 這是整個 Feature 的目的。US1 發出的 key 若不能用來呼叫，它就只是一
串存在資料庫裡的字串（2C-0 開工前定案的原話）。

**Independent Test**: 以一把已存在、scope 只含「讀」的 key 呼叫一個讀端點（成功）與一個寫
端點（被拒），並確認兩次請求都落在該 key 所屬的租戶。

**Acceptance Scenarios**:

1. **Given** 一把有效的 key，**When** 帶著它呼叫一個在其權限範圍內的端點，**Then** 請求被
   當成已認證並正常完成。
2. **Given** 同一把 key，**When** 呼叫一個**不在**其權限範圍內的端點，**Then** 被拒絕，且拒
   絕紀錄指出是哪一項權限擋下的。
3. **Given** 同一把 key，**When** 請求中同時夾帶指定其他租戶的資訊，**Then** 生效的租戶仍
   是 key 本身所屬的那一個——呼叫端自報的租戶一律不被採信。
4. **Given** 一把 key 的持有者**不是**建立它的人，且建立者事後被授予了更多權限，**When** 用
   該 key 呼叫新權限涵蓋的端點，**Then** 仍被拒絕——key 的權限是發放當下寫死的清單。
5. **Given** 一把已撤銷的 key，**When** 用它呼叫任何端點，**Then** 認證失敗。
6. **Given** 一把已過期的 key，**When** 用它呼叫任何端點，**Then** 認證失敗。
7. **Given** 一串格式正確但不存在的 key，**When** 用它呼叫，**Then** 認證失敗，且其回應
   **與「已撤銷」「已過期」兩種情況無法區分**——回應內容與回應時間都不得洩漏這把 key 是否
   曾經存在。
8. **Given** 一把有效的 key，**When** 用它呼叫平台上任何一個端點，**Then** 放行與否**只由
   該 key 的權限範圍決定**——不存在一份「API Key 不准碰」的端點清單。
9. **Given** 一把權限範圍含 API Key 管理權限的 key，**When** 用它建立另一把 key，**Then**
   成功，且新的那一把 MUST 同樣受權限不得擴大的規則約束（見 Story 5）。

### User Story 3 - 稽核與帳分得出這件事是機器做的，還是人做的 (Priority: P2)

租戶的管理者在稽核紀錄裡看到一連串知識庫的變更。他要能一眼分辨哪些是同事在介面上做的、哪
些是那個外部整合做的；出事時要指得出**是哪一把 key**，才知道該撤哪一把。

**Why this priority**: 這是本 Feature 唯一修正**既有錯誤資料**的部分——在它之前，機器做的
事被記成人做的（見背景）。但它不影響 US1／US2 是否能運作，因此排在其後。

**Independent Test**: 用一把 key 完成一次會留稽核的操作，檢查該筆紀錄的 actor 類型與指認
對象；再以人的身分做同一件事，檢查兩者可區分。

**Acceptance Scenarios**:

1. **Given** 一把 key 完成了一次會留稽核的操作，**When** 檢視該筆稽核，**Then** 其 actor
   類型標示為 API Key，**且指得出是哪一把**。
2. **Given** 同一種操作由人透過介面完成，**When** 檢視稽核，**Then** 其 actor 類型仍是使用
   者——既有行為不得因本 Feature 而改變。
3. **Given** 一把 key 的請求因權限不足被拒，**When** 檢視稽核，**Then** 該筆被拒紀錄同樣
   指得出是哪一把 key，以及被哪一項權限擋下。
4. **Given** 一把 key 觸發了會計費的操作，**When** 檢視用量與成本紀錄，**Then** 該筆用量
   計入該 key 所屬的租戶，**且指得出是哪一把 key 花的**。
5. **Given** 同一租戶下人與 key 各自產生的用量，**When** 管理者檢視帳，**Then** 兩者可分開
   計算——「這個月哪個整合花最多」是一個答得出來的問題。
6. **Given** 建立與撤銷 key 這兩個動作本身，**When** 檢視稽核，**Then** 兩者都有紀錄，且
   **紀錄中不含 key 的明文**。

---

### User Story 4 - 看得出哪一把還在用、哪一把可以收掉 (Priority: P2)

租戶用了半年，累積了七八把 key。管理者要決定哪些可以撤掉，他需要知道每一把**上次被用是什
麼時候**，以及哪些已經到期。他不希望為了得到這個資訊，讓每一次 API 呼叫都多付一次寫入的
代價。

**Why this priority**: 沒有這一層，key 只會愈積愈多，而且沒有人敢撤——「不知道還有沒有人在
用」是撤不掉的唯一理由。但它不阻擋 US1／US2。

**Independent Test**: 用一把 key 密集呼叫一段時間，檢查它的「最後使用時間」有更新、而更新
的次數遠少於呼叫次數；另檢查一把設了到期時間的 key 在到期後的狀態呈現。

**Acceptance Scenarios**:

1. **Given** 一把 key 被使用，**When** 管理者查看它，**Then** 看得到它最後一次被使用的時間。
2. **Given** 一把 key 在短時間內被使用非常多次，**When** 觀察系統對「最後使用時間」的更新，
   **Then** 更新次數**顯著少於**呼叫次數——這個欄位不得使每一次呼叫都變成一次寫入。
3. **Given** 一把從未被使用過的 key，**When** 管理者查看它，**Then** 「從未使用」與「很久沒
   用」是可區分的兩種狀態。
4. **Given** 一把設有到期時間的 key，**When** 到期時間經過，**Then** 它在清單上呈現為已過期，
   且不再能通過認證（承 US2 情境 6）。
5. **Given** 一把已撤銷的 key，**When** 管理者嘗試恢復它，**Then** 做不到——撤銷不可復原，
   要繼續用只能建立新的一把。

---

### User Story 5 - 發放者不能藉由發鑰匙把自己沒有的權力交出去 (Priority: P2)

一位權限有限的管理者在建立 key 時，指定了一組超出他自己權限的範圍。系統必須擋下來。

**Why this priority**: 這是**權限自我提升**的標準路徑，而且它偽裝得很好——所有動作都是合法
的：他有建立 key 的權限，他建立了一把 key。10 §3 對自訂角色已經寫下同一條規則（「授予他人
的權限 ⊆ 自己的權限」），API Key 是同一個問題的第二個入口。

**Independent Test**: 以一位不具備某項權限的管理者，嘗試建立含該項權限的 key，確認被拒。

**Acceptance Scenarios**:

1. **Given** 一位具備 API Key 管理權限、但不具備某項資料權限的使用者，**When** 建立一把
   scope 含該項資料權限的 key，**Then** 被拒絕，且訊息指出是哪一項超出範圍。
2. **Given** 同一位使用者，**When** 建立一把 scope 完全落在自己權限內的 key，**Then** 成功。
3. **Given** 一份含不存在權限碼的 scope，**When** 用它建立 key，**Then** 被拒絕——scope 只能
   由系統已定義的權限碼組成。
4. **Given** 一把已建立的 key，**When** 其建立者事後被移除某項權限、被停用、甚至被刪除，
   **Then** 該 key **不受影響**——它自建立的那一刻起就是一份獨立憑證，權限是當時寫定的那份
   清單。要停掉它只有一個動作：撤銷它。
5. **Given** 一把 key 的建立者帳號已被刪除或匿名化，**When** 管理者檢視該 key，**Then** 仍
   看得到「這把是誰發的」這項紀錄——**發放的事實不隨帳號一起消失**。

---

### Edge Cases

- 一把 key 在請求處理到一半時被撤銷：這一次請求算不算數？（撤銷「立即生效」的邊界是每一次
  請求的開始，還是每一次權限判定？）
- 同一個請求同時帶了使用者的 token 與一把 key：以哪一個為準？還是直接拒絕？**兩者屬於不同
  租戶時尤其危險**。
- key 的明文出現在請求的 URL 而不是標頭裡（呼叫端寫錯）：它會不會被寫進存取日誌？
- 明文出現在錯誤訊息、稽核紀錄、例外堆疊或前端可見的回應中——本 Feature 新增的每一條路徑都
  必須被檢查過一次。
- 大量以隨機字串嘗試的請求（猜 key）：認證失敗的成本是否低到可以被當成掃描工具使用？
- 一把 key 的權限範圍是空的（不含任何權限碼）：這是合法的「先建後給」，還是無意義而應拒絕？
- 一把 key 發出的 key，其到期時間**晚於**發放它的那一把：撤掉母鑰匙不會撤掉子鑰匙
  （FR-014b 明訂不做連鎖撤銷），那麼盤點時要怎麼看出這條鏈？
- 到期時間設在過去：建立時就該拒絕，還是允許並立即呈現為已過期？
- 一個租戶累積數百把 key：列出時的效能與可用性。
- key 的前綴恰好相同（碰撞）：辨識用的前綴是否保證唯一？

## Requirements *(mandatory)*

### Functional Requirements

**發放與管理（Story 1）**

- **FR-001**: 租戶管理者 MUST 能建立 API Key，並於建立時指定名稱、權限範圍與到期時間。
- **FR-002**: 建立時 MUST 回傳完整明文**恰好一次**；此後系統 MUST NOT 存在任何可讀回明文的
  路徑——清單、查詢、稽核紀錄、日誌、錯誤訊息與任何回應皆不得包含明文或可還原明文的資料。
- **FR-003**: 系統 MUST 為每一把 key 保留一段足以辨識它的短前綴，供人在清單上對照使用；該
  前綴 MUST NOT 足以推得明文。
- **FR-004**: 管理者 MUST 能列出本租戶的所有 key，內容含名稱、前綴、權限範圍、建立者、建立
  時間、到期時間、最後使用時間與目前狀態。
- **FR-005**: 管理者 MUST 能撤銷本租戶的任一把 key；撤銷 MUST 立即生效，且 MUST NOT 可復原。
- **FR-006**: 建立、列出、撤銷三個動作 MUST 要求一項專屬的管理權限，且該權限 MUST NOT 屬於
  一般成員的預設權限。
- **FR-007**: 一把 key MUST 只屬於一個租戶；跨租戶的列出、查詢與撤銷 MUST 失敗。

**認證（Story 2）**

- **FR-008**: 帶有有效 key 的請求 MUST 被視為已通過認證的呼叫者，且系統 MUST 以此建立完整
  的請求身分——後續所有租戶隔離機制的行為 MUST 與使用者身分時一致。
- **FR-009**: 請求生效的租戶 MUST 完全由 key 本身決定；呼叫端自報的租戶資訊 MUST NOT 被採信。
- **FR-010**: 一把 key 的可用權限 MUST 是它建立時指定的權限範圍，MUST NOT 隨建立者事後獲得
  新權限而擴大。
- **FR-011**: 超出權限範圍的請求 MUST 被拒絕，且拒絕 MUST 記錄被擋下的權限項目（沿用既有的
  拒絕紀錄語意）。
- **FR-012**: 不存在、已撤銷與已過期的 key MUST 產生**同一種**認證失敗結果；回應的內容與
  回應所需的時間 MUST NOT 使呼叫端分辨出這把 key 是否曾經存在。
- **FR-013**: 請求同時帶有使用者憑證與 API Key 時，系統 MUST 有唯一且明確的處置，MUST NOT
  依端點或處理順序而異。
- **FR-014**: API Key MUST 能呼叫平台的**全部端點**，放行與否**只由該 key 的權限範圍決定**
  （2026-09-06 人類裁決）。系統 MUST NOT 另外維護一份「API Key 不准碰」的端點清單——單一
  判定入口是這條規則存在的目的：兩套判定必然有一天不一致，而不一致的症狀是「某個端點沒有
  被保護」而非任何錯誤訊息。
- **FR-014a**: 承 FR-014，一把權限範圍含 API Key 管理權限的 key MUST 能發出新的 key。因此
  「發放者」這個概念 MUST 同時涵蓋使用者與 API Key 兩種形態，FR-016 的約束 MUST 對兩者
  同等適用。
- **FR-014b**: 由 key 發出的 key MUST 記錄其發放者是哪一把 key（承 FR-017 的可指認要求），
  使一條發放鏈事後追得回來。**本 Feature MUST NOT 讓撤銷一把 key 連帶撤銷它發出的 key**
  ——連鎖撤銷是另一個機制，而在它存在之前，可追溯是止血時唯一能依靠的東西。

**權限範圍的正當性（Story 5）**

- **FR-015**: 權限範圍 MUST 只能由系統已定義的權限碼組成；含未定義權限碼的建立請求 MUST 被
  拒絕。
- **FR-016**: **發放者**——使用者或 key，兩者皆然（FR-014a）——MUST NOT 能授予自己不具備的
  權限；違反時 MUST 拒絕並指出超出的項目。對使用者而言「自己具備的權限」是其角色的權限
  總和，對 key 而言是它自己的權限範圍。

**稽核與用量（Story 3）**

- **FR-017**: 由 key 發起的操作，其稽核紀錄的 actor 類型 MUST 標示為 API Key，且 MUST 指認
  到具體是哪一把。
- **FR-018**: 由使用者發起的操作，其稽核紀錄的既有語意 MUST NOT 因本 Feature 而改變。
- **FR-019**: 建立與撤銷 key 這兩個動作本身 MUST 入稽核，且 MUST NOT 含明文。
- **FR-020**: 由 key 觸發的計費用量 MUST 計入該 key 所屬租戶，既有的配額判定語意 MUST NOT
  改變。
- **FR-020a**: 用量紀錄 MUST 指得出是哪一把 key 花的（2026-09-06 人類裁決），且人與 key 產
  生的用量 MUST 可分開統計。既有用量紀錄的欄位語意 MUST NOT 改變，既有查詢在不指定 key 時
  的結果 MUST 與本 Feature 之前一致。

**生命週期（Story 4）**

- **FR-021**: key MUST 支援到期時間；已過期的 key MUST 無法通過認證，且 MUST 在清單上呈現
  為已過期。
- **FR-022**: 系統 MUST 記錄每把 key 最後一次被使用的時間，且該記錄的寫入 MUST 被節流——
  MUST NOT 使每一次成功認證都產生一次持久化寫入。
- **FR-023**: 「從未被使用」與「曾被使用但已久未使用」MUST 為可區分的兩種狀態。
- **FR-024**: key 的有效性 MUST 完全獨立於其建立者（2026-09-06 人類裁決）：建立者被降權、
  停用或刪除，**MUST NOT** 使 key 失效或縮小其權限範圍。停用一把 key 的唯一動作是撤銷它。
- **FR-024a**: 承 FR-024，「這把 key 是誰發的」MUST 在建立者帳號被刪除或匿名化之後仍然
  查得到——發放紀錄 MUST NOT 因帳號生命週期而消失，亦 MUST NOT 反過來擋住帳號的刪除。
- **FR-024b**: 由於 key 不隨人失效，系統 MUST 讓「這個租戶目前有哪些 key 有效」在任何時候
  都答得出來（承 FR-004）——這是本裁決之下唯一的盤點手段。

**文件同步**

- **FR-025**: API 契約文件、安全設計文件、資料庫設計文件與開發 Roadmap MUST 同步本 Feature
  造成的行為變更；Roadmap 的 2C-3 條目 MUST 依實作結果結案，並 MUST 記下 2C 切分表中
  「API Key 前端畫面歸 2C-5」這項 2026-09-06 的裁決。

### Key Entities

- **API Key**：一個租戶發放給機器的憑證。屬性：所屬租戶、名稱、可辨識的短前綴、權限範圍、
  建立者、建立時間、到期時間、最後使用時間、狀態（有效／已撤銷／已過期）。**明文不是它的
  屬性**——明文只在建立的那一次存在於回應裡，之後系統只保有無法反推明文的驗證材料。
- **呼叫者（Principal，擴充）**：既有概念。原本只有一種形態（登入的使用者），本 Feature 讓
  它有第二種（API Key）。兩種形態都必須帶著租戶與一組有效權限；差別在於使用者的權限來自
  角色，而 key 的權限來自發放時寫定的範圍。
- **稽核紀錄（擴充）**：既有實體。它的「這是誰做的」早已允許三種答案，而其中的 API Key 這
  一種在本 Feature 之前無法被寫出；本 Feature 讓它成立。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 一個外部系統能在**完全不持有任何人類帳號密碼**的前提下完成一次完整的資料存取
  ——此項目前的成功率為 **0%**（沒有這條路）。
- **SC-002**: key 的明文在建立之後於系統中的可讀回次數為 **0**：清單、查詢、稽核、日誌、
  錯誤訊息五個位置逐一檢查皆查不到。
- **SC-003**: 撤銷之後的下一次呼叫失敗率 **100%**，且從撤銷到失效之間不存在可觀測的延遲窗口。
- **SC-004**: 超出權限範圍的呼叫成功率 **0%**，且每一次都留下指出被擋權限的紀錄。
- **SC-005**: 由 key 發起的操作在稽核上被指認為機器且指得出是哪一把的比例為 **100%**——此項
  目前為 **0%**（機器的動作被記成人的動作，且無任何症狀）。
- **SC-006**: 跨租戶的列出、撤銷與呼叫成功率 **0%**。
- **SC-007**: 「不存在」「已撤銷」「已過期」三種 key 的失敗回應，在內容上完全相同，在耗時
  分布上無法據以判別——外部觀察者無法藉由回應推測一把 key 是否曾經存在。
- **SC-008**: 一把在短時間內被使用 N 次的 key，其「最後使用時間」的持久化寫入次數為 N 的
  極小比例；同時該時間與真實最後使用時間的落差有明確且可驗證的上界。
- **SC-009**: 一位權限有限的管理者無法藉由建立 key 取得自己沒有的權限——嘗試的成功率 **0%**。
- **SC-010**: 本 Feature 完成後，既有的使用者登入路徑行為完全不變：既有的認證、權限與稽核
  測試全部維持通過，無需修改斷言。
- **SC-011**: 「本租戶這個月哪一把 key 花了多少」是一個答得出來的問題，且答案與該租戶的用量
  總額對得起來——人與機器的用量相加等於租戶總額，不多不少。
- **SC-012**: 一把 key 的建立者被停用或刪除之後，該 key 的可用性 **100% 不變**；同時「這把
  是誰發的」仍然查得到。
- **SC-013**: 由 key 發出的每一把 key，其發放鏈都追得回源頭——追溯成功率 **100%**。這一項
  是端點範圍採全開（FR-014）之後唯一的補償措施，因此它不成立時，該裁決的風險就沒有著落。

## Assumptions

以下是在描述未指明處採用的合理預設，**它們是需求的一部分，不是實作細節**；若 review 時不同
意，請直接改這一節。

- **撤銷不可復原、無軟刪除的復原路徑**：沿用 2C-2 憑證表的既有慣例（「無軟刪除」）。要繼續
  用只能建立新的一把。
- **到期時間為選填**：未設到期的 key 有效直到被撤銷。強制到期會讓每一個整合在某天無預警斷
  線，而本 Feature 尚未提供到期前的通知機制（見 Out of Scope）。
- **建立時的到期時間不得早於當下**：設在過去的到期時間在建立時就拒絕，而不是建立一把出生
  即過期的 key。
- **權限範圍不得為空**：空範圍的 key 什麼也做不了，允許它只會製造「明明有 key 卻一直被拒」
  的支援案件。
- **配額仍以租戶為單位**：2A 的 quota 語意不變，本 Feature **不**新增按 key 的獨立配額。
- **管理權限授予 Owner 與 Admin 兩個系統角色**：系統角色不可修改（10 §3），因此哪些角色拿
  得到這項權限是一個需求決定；Editor 與 Viewer 不得擁有。
- **key 的明文格式、雜湊方式、驗證的資料存取路徑屬 plan 層**，本 spec 只要求「明文不落地、
  驗證不需要掃全表」這兩個可觀測的性質。
- **本 Feature 不設每租戶 key 數量上限**；若列出效能成為問題，屬後續調整。
- **前端畫面不在本 Feature**：2026-09-06 人類裁決歸 2C-5，與管理面版型一起做。

### 2026-09-06 三項裁決帶進來的前提

三個問題都選了「最不設限」的那一個，代價是明確的，寫在這裡以免日後被讀成疏忽：

- **端點全開（FR-014）**：key 可以發 key，而撤銷不連鎖（FR-014b）。因此「撤掉一把 key」
  **不等於**止血完成——止血的完整動作是「撤掉它，並沿發放鏈檢查它發出過什麼」。這使
  FR-004 的清單與 FR-014b 的發放鏈從方便功能升格為**安全機制**。
- **用量指認到 key（FR-020a）**：既有用量紀錄是按月分區的 append-only 資料，本 Feature 要
  為它增加一項識別。**既有紀錄不會有這項值**，因此任何統計都必須容得下「舊資料沒有」而不是
  把它當成「不是 key 花的」——兩者在圖表上看起來一模一樣。
- **key 完全獨立於建立者（FR-024）**：離職者發出的 key 會活下去。本 Feature **不**提供任何
  自動回收，盤點完全依賴 FR-004 的清單與 FR-022 的最後使用時間。這是刻意的取捨——把 key 綁
  回人，等於把本 Feature 要解開的那條綁定又綁回去。

## Dependencies

- **既有的權限碼字典**：scope 是它的子集，本 Feature 依賴它作為 scope 的合法值來源，並需要
  向其新增一項 API Key 管理權限。
- **既有的認證與租戶脈絡機制**：本 Feature 新增的是第二種進入方式，不是第二套隔離機制——
  租戶隔離的行為必須與既有路徑完全一致。
- **既有的稽核紀錄管道**：其「這是誰做的」欄位早已把 API Key 列為合法答案之一（05 §179），
  本 Feature 讓那個答案第一次真的被寫出。
- **2A 的用量與配額**：由 key 觸發的計費要落在既有的記帳路徑上。

## Out of Scope

- **前端畫面**（歸 2C-5，2026-09-06 人類裁決）。
- **per-key IP allowlist 與 HMAC request signing**：10 §2.2 明列為未來 enterprise plan。
- **按 key 的獨立配額或速率限制**。
- **key 的自動輪替、到期前通知、即將到期提醒**。
- **連鎖撤銷**（撤一把 key 時連帶撤銷它發出的 key）：FR-014b 明訂不做，本 Feature 只保證那
  條鏈**追得回來**。
- **自訂角色與資源級 grant**（延後至 Phase 5，見 13 §4 的 2C 裁切說明）。
- **平台級（跨租戶）的 API Key**：本 Feature 的每一把 key 都屬於單一租戶。
