# Feature Specification: PDF 掃描頁與內嵌圖的檢索（W2 圖片 RAG）

**Feature Branch**: `002-pdf-image-rag`

**Created**: 2026-09-05

**Status**: Draft

**Input**: User description: "W2 圖片 RAG：讓 PDF 裡的掃描頁與內嵌圖變得檢索得到。圖片不進向量空間——OCR 取出的文字 ＋ VLM 生成的 caption ＋ 既有圖說 ＋ 前後文組成文字進 Chunk.content，原圖留在物件儲存。不做 CLIP 第二路、不做 ColPali。原圖只在使用者追問時才送進 vision context。caption 是生成文字，必須標記；引用渲染的是原圖；圖片 URL 走短效 presigned 且過租戶檢查；不可讓 LLM 吐 markdown 圖片語法。本次只含 PDF（掃描頁與內嵌圖），不含 Office 內嵌圖、不含直接上傳圖片檔。既有已 ready 的文件要能由人逐 KB 觸發重新抽取。對齊 docs/plan/13 §4.2 的 W2 定案。"

## 背景（為什麼需要這個 Feature）

系統對「PDF 裡的圖」目前有兩種失敗方式，而它們的嚴重程度剛好相反。

**第一種是吵的**：沒有文字層的掃描件在抽取時直接判失敗，訊息寫著「PDF 沒有可抽取的文字層
（掃描件需 OCR，目前未啟用）」。這是 1B 的刻意選擇——回一份空文件的話，文件會走完整條
ETL 停在 `ready` 而一個段落都沒有，使用者只會覺得「這份好像沒被讀進去」，沒有任何地方
看得出原因。所以掃描件的現況是**明確地進不來**。

**第二種是安靜的**：有文字層的 PDF 照常處理成功、狀態 `ready`、看起來一切正常，而那份
文件裡的每一張圖——架構圖、流程圖、螢幕截圖、圖表——**完全不存在於索引裡**。使用者問
「那張架構圖裡 API 接到哪一層」，系統回答找不到，而那個回答看起來就像文件裡沒寫。
**這一種沒有任何錯誤訊息，也沒有任何測試會紅。**

第二種才是這個 Feature 真正的理由。第一種至少誠實。

還有一件事使這個 Feature 的形狀被提前決定了：圖片一旦要「被找得到」，最直覺的做法是把圖
本身編碼成向量、另開一條檢索路。**那條路已經在 2026-08-30 被明確否決**，理由不是成本而是
它會弄壞目前最有效的那一關——純圖向量那一路沒有 passage text，rerank 跑不了，而 rerank 是
2B-4 實測 recall@1 `0.4375 → 0.7917` 的最大槓桿。用「多一條檢索路」換掉「最有效的那一關」
不划算。因此本 Feature 的核心限制是：**圖片的內容要變成文字才進索引，圖本身不進向量空間。**

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 掃描件不再被擋在門外，而且問得到裡面的內容 (Priority: P1)

使用者上傳一份掃描的合約或報告（整份都是影像、沒有文字層）。目前這一步就失敗。他要的是
文件正常處理完成，然後可以問裡面的內容並得到帶引用的答案。

**Why this priority**: 這是目前唯一**完全進不來**的一類文件；其餘故事處理的是「進來了但看
不到一部分」。少了它，掃描件的使用者連第一步都走不到。

**Independent Test**: 上傳一份純掃描 PDF，等到處理完成，就其中一段內容提問，檢查答案的引用
指到正確的頁。不需要本 Feature 的任何其他部分。

**Acceptance Scenarios**:

1. **Given** 一份沒有文字層的 PDF，**When** 上傳並等待處理完成，**Then** 文件狀態為可檢索，
   且產生的段落數大於零。
2. **Given** 該文件已可檢索，**When** 就其中一段影像上的文字提問，**Then** 得到答案且引用
   指向該內容所在的頁。
3. **Given** 一份影像上完全沒有可辨識文字的 PDF（例如整份只有照片），**When** 上傳並處理，
   **Then** 系統**不得**回報成功但零段落——它必須產出可檢索的內容，或明確失敗並說明原因。

---

### User Story 2 - 有文字層的文件裡，那些圖的內容也找得到 (Priority: P2)

使用者上傳一份技術文件，正文是文字、關鍵資訊在幾張架構圖與圖表裡。他問「使用者請求先經過
哪一層」，答案就畫在圖上。目前這個問題必定答不出來，而且看起來像文件沒寫。

**Why this priority**: 這是安靜的那一種失敗，數量上也遠多於純掃描件——但它的前置（圖片的
抽取、保存、轉成文字）與 Story 1 共用同一條路徑，因此排在其後。

**Independent Test**: 上傳一份含圖的 PDF，就「只畫在圖上、正文沒寫」的一項資訊提問，檢查
是否答得出來並引用到該圖所在的位置。

**Acceptance Scenarios**:

1. **Given** 一份有文字層且含圖的 PDF，**When** 處理完成，**Then** 每一張被處理的圖都對應
   到至少一段可檢索的文字。
2. **Given** 圖上有文字（例如流程圖的節點標籤），**When** 就那些文字提問，**Then** 找得到
   該段並引用到圖所在的頁。
3. **Given** 圖上沒有文字（例如一張照片或示意圖），**When** 就圖的內容提問，**Then** 仍找得
   到——由圖產生的描述文字負責這一段。
4. **Given** 一張圖，**When** 檢視它產生的段落，**Then** 該段落保有這張圖在文件中的位置
   （頁碼與所屬標題階層）與它的前後文，而不是一段脫離上下文的孤立描述。

---

### User Story 3 - 使用者分得出哪一段是機器描述的，而且點得回原圖 (Priority: P2)

答案引用了一段文字，那段文字是機器看圖寫出來的。使用者必須能一眼看出這件事，並且點開看到
**那張原圖**——而不是機器寫的那段話。他要自己判斷機器有沒有看錯。

**Why this priority**: 由圖產生的描述是**生成內容**，它與文件原文的可信度不同。把兩者混在
一起呈現，等於讓模型的猜測穿上原文的外衣；而使用者對「文件裡寫的」與「AI 猜的」有完全不同
的採信標準。這一層不做，Story 2 產出的每一段都帶著看不見的風險。

**Independent Test**: 就一段由圖產生的內容提問，檢查引用上是否標示為生成內容，以及點開後
呈現的是原圖。

**Acceptance Scenarios**:

1. **Given** 一段由圖產生的文字，**When** 它出現在答案的引用中，**Then** 該引用明確標示這是
   機器產生的描述，而非文件原文。
2. **Given** 同上引用，**When** 使用者展開它，**Then** 看到的是**原圖**；描述文字可以一併
   顯示，但不得取代原圖。
3. **Given** 同上引用，**When** 使用者所屬租戶對該文件沒有讀取權，**Then** 取不到那張圖。
4. **Given** 取得圖片的連結，**When** 超過有效期後再次使用，**Then** 取不到。
5. **Given** 模型的回答文字，**When** 檢視其內容，**Then** 其中不含可被直接渲染的圖片語法
   ——圖片一律由前端依引用資料呈現，不由模型的輸出決定。

---

### User Story 4 - 一份圖很多的文件不會把額度和時間燒光 (Priority: P2)

使用者上傳一份 300 頁、每頁都是掃描影像的文件。他不希望這一次上傳吃掉整個月的額度，也不
希望知識庫因此卡住幾個小時；而如果真的處理不完，他要看得出來哪些處理了、哪些沒有。

**Why this priority**: 由圖產生描述是**每張圖一次模型呼叫**——這是本 Feature 唯一與文件大小
成正比的新成本，而它的上界目前不存在。少了這一層，Story 1 與 Story 2 在真實文件上會變成
一個沒有煞車的計費裝置。

**Independent Test**: 以一份圖片數超過上限的文件檢查：處理是否在上限處停止、文件是否仍可
檢索、被略過的部分是否有記錄、以及每一次描述生成是否都入了帳。

**Acceptance Scenarios**:

1. **Given** 一份圖片數超過單份上限的文件，**When** 處理完成，**Then** 文件仍為可檢索狀態，
   且被略過的圖片數量有明確記錄。
2. **Given** 任一次由圖產生描述的模型呼叫，**When** 它完成，**Then** 該次用量與成本記在發起
   它的租戶名下。
3. **Given** 某一張圖處理失敗（無法辨識、服務逾時、內容無法解析），**When** 整份文件處理
   完成，**Then** 文件仍為可檢索狀態，其餘內容照常可查，且該張圖的失敗有記錄。
4. **Given** 同一份文件的同一個版本，**When** 重複處理，**Then** 不產生重複的段落，也不重複
   計費。

---

### User Story 5 - 既有的文件可以由人回頭補上 (Priority: P3)

知識庫裡已經有幾百份處理過的文件，它們當初的圖全部沒被處理。維護者要能挑一個知識庫、明確
地按下重跑，讓那些文件回到抽取那一步重做一次。

**Why this priority**: 沒有它，語料會長期處在「有些文件的圖看得到、有些看不到」的混合狀態，
而這種不一致沒有任何錯誤訊息。但新上傳的文件不受影響，因此排在後面。

**Independent Test**: 對一個含既有文件的知識庫觸發重跑，檢查重跑前問不到的圖片內容在重跑後
問得到，且重跑期間該知識庫的既有檢索結果維持可用。

**Acceptance Scenarios**:

1. **Given** 一個含既有文件的知識庫，**When** 維護者觸發重新抽取，**Then** 那些文件回到抽取
   那一步重做，其中的圖片被處理成可檢索的文字。
2. **Given** 重新抽取進行中，**When** 使用者對該知識庫提問，**Then** 仍得到答案——重跑期間
   不得出現「文件都在、狀態正常、卻一筆都查不到」的空窗。
3. **Given** 一次重新抽取，**When** 維護者查詢它的狀態，**Then** 看得到進度與結果。
4. **Given** 同一個知識庫，**When** 重複觸發重新抽取，**Then** 不產生重複段落、不重複計費。
5. **Given** 系統整體，**When** 沒有人觸發，**Then** 不對任何知識庫自動執行重新抽取。

---

### User Story 6 - 追問那張圖時，模型才真的看到它 (Priority: P3)

使用者看到一筆由圖產生的引用，覺得描述不夠，於是追問「這張圖右下角那塊寫什麼」。這一次、
也只有這一次，原圖被交給模型去看。

**Why this priority**: 它是描述不足時的補救路徑，而不是主要路徑——把原圖隨每次檢索附上，
代價是每次提問都變成多模態呼叫，成本與延遲對所有使用者生效，換來的只是少數幾次追問。
它同時是本 Feature 唯一需要系統具備「看圖」能力的部分（見 Assumptions）。

**Independent Test**: 對一筆由圖產生的引用追問，檢查該次呼叫是否帶上原圖；並檢查一般提問
的呼叫**不帶**任何圖片。

**Acceptance Scenarios**:

1. **Given** 一次一般的提問，**When** 檢索到由圖產生的段落，**Then** 送給模型的內容**不含**
   任何原圖，只含文字。
2. **Given** 一筆由圖產生的引用，**When** 使用者針對它追問，**Then** 該張原圖被交給模型，
   且該次呼叫的用量記在該租戶名下。
3. **Given** 系統當前設定的模型不具備看圖能力，**When** 使用者針對圖片追問，**Then** 系統
   明確告知這件事，**不得**靜默地退回純文字回答而讓使用者以為模型看過那張圖。

---

### Edge Cases

- 一張圖既沒有可辨識文字、也產不出有意義的描述時，是產出一段近乎空白的內容，還是不產出？
  （不產出時，該圖在索引中不存在這件事是否有記錄可查？）
- 掃描頁的辨識結果全是雜訊字元時，那一段進了索引會污染檢索——如何判定「辨識失敗」而不是
  「這頁本來就是這些字」？
- 同一張圖在一份文件中重複出現（頁首圖標、浮水印、每頁的公司 logo）：會不會產生數十段幾乎
  相同的內容，把檢索結果洗掉？
- 極小的裝飾性圖片（分隔線、項目符號圖標）是否值得一次模型呼叫？
- 圖片處理所依賴的服務不可用時：整份文件失敗、還是退回只處理文字？兩者對使用者的意義完全
  不同（前者是「沒進來」，後者是「進來了但少一半而看不出來」）。
- 一份文件在重新抽取進行中被刪除。
- 租戶額度在一份文件處理到一半時用完：已處理的部分算不算數？
- 影像方向錯誤（旋轉 90 度的掃描頁）。
- 圖片內容含個人資料（身分證掃描件）：描述文字會把影像裡的個資變成可全文檢索的文字。

## Requirements *(mandatory)*

### Functional Requirements

**抽取與索引（Story 1、Story 2）**

- **FR-001**: 沒有文字層的 PDF MUST 產出可檢索的文字內容，MUST NOT 再因「沒有文字層」而
  整份判為失敗。
- **FR-002**: 有文字層的 PDF 中的內嵌圖 MUST 各自產出可檢索的文字內容。
- **FR-003**: 由圖產生的文字 MUST 同時包含**影像上辨識出的文字**與**對影像內容的生成描述**
  （兩者都取得到時），並 MUST 保留該圖在文件中的位置（頁碼、所屬標題階層）與其前後文。
- **FR-004**: 圖片的原始影像 MUST 保存於物件儲存，且由它產生的每一段文字 MUST 能追回對應的
  那一張原圖。
- **FR-005**: 圖片 MUST NOT 進入向量空間；本 Feature MUST NOT 新增第二條檢索路徑——檢索仍
  只在文字上進行。
- **FR-006**: 單一張圖片的處理失敗 MUST NOT 導致整份文件失敗；失敗 MUST 有記錄。
- **FR-007**: 上傳的內容型別白名單 MUST 維持不變——本 Feature MUST NOT 新增可上傳的檔案
  型別，亦 MUST NOT 改動上傳大小上限與配額的計算語意。

**標示、引用與存取（Story 3）**

- **FR-008**: 由圖產生的描述 MUST 被標示為生成內容，且該標示 MUST 從產生的那一刻起一路保留
  到使用者看到的引用上，中途 MUST NOT 遺失。
- **FR-009**: 引用一段由圖產生的內容時，呈現給使用者的 MUST 是**原圖**；描述文字 MAY 一併
  顯示，但 MUST NOT 取代原圖。
- **FR-010**: 取得圖片的連結 MUST 為短效，且 MUST 經過租戶與文件讀取權檢查；逾期或跨租戶的
  取用 MUST 失敗。
- **FR-011**: 模型的輸出 MUST NOT 包含可被直接渲染的圖片語法；圖片一律由前端依引用資料
  呈現。

**模型看圖的時機（Story 6）**

- **FR-012**: 原圖 MUST NOT 隨一般檢索附加到送給模型的內容中。
- **FR-013**: 使用者針對某一筆由圖產生的引用追問時，系統 MUST 能將該張原圖交給模型；若當前
  模型不具備此能力，MUST 明確告知，MUST NOT 靜默退回純文字。

**成本、資源與冪等（Story 4）**

- **FR-014**: 每一次為產生描述而發出的模型呼叫 MUST 計入發起它的租戶的用量與成本記錄。
- **FR-015**: 單份文件可處理的圖片數量 MUST 有上限；達到上限時 MUST 停止處理其餘圖片、
  MUST 記錄被略過的數量，且該文件 MUST 仍為可檢索狀態。
- **FR-016**: 圖片處理 MUST 冪等——同一份文件的同一個版本重複處理，MUST NOT 產生重複段落、
  MUST NOT 重複計費。
- **FR-017**: 每一次影像辨識與描述生成 MUST 有逾時；逾時 MUST 視為該張圖處理失敗（FR-006），
  而非整份文件失敗。

**既有文件的回補（Story 5）**

- **FR-018**: 系統 MUST 提供由人逐知識庫觸發的**重新抽取**，其語意是讓文件回到抽取那一步
  重做——與既有的「重建索引」（重切段落並重算向量）MUST 為可區分的兩件事。
- **FR-019**: 重新抽取 MUST 可查詢進度與結果，MUST 冪等，且執行期間該知識庫的既有檢索結果
  MUST 維持可用。
- **FR-020**: 重新抽取 MUST 只由明確的人為動作觸發，MUST NOT 自動對全庫執行。

**租戶隔離與生命週期**

- **FR-021**: 圖片物件 MUST 受租戶隔離；跨租戶的取用 MUST 失敗。
- **FR-022**: 文件或知識庫被刪除時，其圖片物件 MUST 進入既有的資料清理路徑，MUST NOT 成為
  永久殘留。

**可觀測性**

- **FR-023**: 每份文件 MUST 記錄其圖片處理的統計：圖片總數、成功辨識數、成功產生描述數、
  失敗數、因上限而略過數。

**文件同步**

- **FR-024**: ETL 設計文件、AI Pipeline 文件、API 契約文件與開發 Roadmap MUST 同步本
  Feature 造成的行為變更；Roadmap 的 W2 條目 MUST 依實作結果結案。

### Key Entities

- **圖片產出物（Image Artifact）**：一份文件中的一張圖。屬性：所屬文件與版本、在文件中的
  位置（頁碼、序）、原始影像的儲存位置、處理狀態（成功／失敗／略過）、失敗原因。
- **由圖產生的段落**：進入索引的文字。屬性：來源圖片產出物、辨識出的文字、生成的描述、
  **生成標示**、位置與前後文。它與既有的文字段落在檢索上地位相同——差別只在來源與標示。
- **重新抽取工作（Re-extraction Job）**：一次由人觸發、以知識庫為範圍的回補。屬性：範圍、
  觸發者、狀態、進度、結果統計。
- **引用（Citation，擴充）**：既有實體。本 Feature 為它增加「這一段是不是機器產生的」與
  「對應的原圖在哪」兩項資訊。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 上傳一份純掃描 PDF 後可就其內容提問並得到帶正確頁碼引用的答案——此項目前的
  成功率為 0%（上傳即失敗）。
- **SC-002**: 一份「關鍵資訊只畫在圖上、正文未提及」的 PDF，就該資訊提問能得到答案——此項
  目前的成功率為 0%，且目前的失敗**不產生任何錯誤訊息**。
- **SC-003**: 使用者在任何一筆由圖產生的引用上，100% 分得出那是機器產生的描述而非文件原文。
- **SC-004**: 展開一筆由圖產生的引用時，看到的 100% 是原圖。
- **SC-005**: 圖片取得連結在逾期後、以及在無權租戶手上，取用成功率為 0%。
- **SC-006**: 一份含 N 張圖的文件，其描述生成的模型呼叫次數等於實際處理的圖片張數（不多不
  少），且每一次都出現在該租戶的用量記錄中。
- **SC-007**: 單張圖處理失敗時，該文件仍為可檢索狀態，且其餘內容的可檢索性不受影響。
- **SC-008**: 對同一份文件的同一版本重複處理，新增段落數為 0、新增計費筆數為 0。
- **SC-009**: 本 Feature 完成後，「以圖片作為查詢」這件事仍然做不到——使用者能找到的一律是
  文字，圖片只作為被找到之後呈現的東西。
- **SC-010**: 逐知識庫回補完成後，回補前問不到的圖片內容問得到；回補期間對該知識庫提問的
  可回答率不低於回補前。
- **SC-011**: 一般提問送給模型的內容中，圖片數量為 0。
- **SC-012**: 一份圖片數超過上限的文件處理完成後，仍為可檢索狀態，且被略過的圖片數量可從
  記錄中查得。

## Assumptions

**已定案的範圍限制（2026-08-30 與 2026-09-05 人類裁決，記於 docs/plan/13 §4.2）**

這些是**已經做出的決定**，不是本 Feature 要重新評估的選項；它們約束 Plan 層的技術選擇：

- 圖片**不進**向量空間；由圖產生的**文字**進索引，原圖留在物件儲存。
- **不做** CLIP 第二路、**不做** ColPali——理由是純圖向量那一路沒有 passage text，rerank
  跑不了，而 rerank 是實測 recall@1 `0.4375 → 0.7917` 的最大槓桿。
- 進索引方式為**影像辨識與生成描述兩者都做**（2026-09-05 裁決）。
- 輸入範圍**只含 PDF**（掃描頁與內嵌圖，2026-09-05 裁決）。
- 既有文件的回補為**逐知識庫、由人觸發**（2026-09-05 裁決），非自動、非全庫。

**現況與前提**

- **系統目前不具備「看圖」的能力**：AI Gateway 現有的能力為對話、嵌入與重排三種，沒有
  多模態。Story 6（FR-012／FR-013）是本 Feature 唯一需要新增這項能力的部分，其餘故事都
  不需要——這使 Story 6 成為可獨立排序或延後的一塊。
- **系統目前沒有任何短效連結的產生路徑**：物件儲存的短效授權連結至今未被使用過（大檔直傳
  屬後續工作包）。FR-010 是第一個需要它的需求。
- **W1 的地端嵌入沒有降低本 Feature 的成本**：地端嵌入讓描述文字進向量不再按次計費，但
  描述本身仍是**每張圖一次模型呼叫**；且該地端模型是純文字模型，不提供任何影像編碼能力。
  描述生成跑在本機或雲端屬 Plan 層的手段選擇。
- 影像辨識引擎與描述生成模型的選擇屬 Plan 層，本規格不指定。
- 單份文件的圖片數量上限、短效連結的有效期長度，其**具體數值**於 Plan 層依實測決定；本
  規格只要求它們存在且可設定。
- 文件語言以中文與英文為主，影像辨識需同時支援兩者。
- 掃描件的影像品質假設為一般辦公掃描（≥200 dpi）；手寫內容的辨識品質不在本 Feature 的
  目標內。
- 既有的文件狀態機、切塊策略與檢索參數不因本 Feature 改變。

## Dependencies

- 依賴 1B 建立的 ETL 抽取流程、文件狀態機與隔離執行環境（抽取跑在有逾時的子行程中）。
- 依賴既有的物件儲存與其租戶隔離規則。
- 依賴既有的用量與成本記錄機制（FR-014 是新增一種計費來源，不是新增一套記錄）。
- 依賴 2B-6 的重建索引機制：本 Feature 的「重新抽取」與它是**兩件不同的事**，但兩者在
  「由人逐知識庫觸發、可查進度、冪等」這些形狀上應保持一致，避免使用者面對兩套不同語意的
  重跑。
- **需要兩項新的外部依賴**：影像文字辨識，以及具備看圖能力的模型。兩者的具體選型屬 Plan
  層，但它們的存在本身是本 Feature 的前提。

## Out of Scope

- Office 文件（docx／xlsx）內嵌圖片的處理。
- 直接上傳圖片檔（png／jpg 等）——不新增內容型別白名單項目，不改動配額與大小上限語意。
- 任何以圖片為輸入的向量檢索路徑（CLIP、ColPali 或其他）。
- 影像中表格的結構還原（把圖裡的表格變回可查詢的表格資料）。
- 手寫內容的辨識品質最佳化。
- 影片與音訊。
- 自動對全庫觸發回補。
- 圖片內容的個資偵測與遮罩（Edge Cases 已記下風險；處置屬 3D 安全強化的範圍）。
- 依本 Feature 的結果調整任何既有檢索參數。
