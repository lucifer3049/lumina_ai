# Feature Specification: 換 embedding 模型後的檢索品質重新定錨

**Feature Branch**: `001-eval-rebaseline`

**Created**: 2026-09-05

**Status**: Draft

**Input**: User description: "W1 的 eval 補跑：換成 bge-m3 之後的檢索品質要有數字。手寫題組由 24 題擴充到約 50 題（含跨語言題）；評測報告補記 embedding 維度並納入可比性判斷；新增一條顯式的跨模型比較路徑（明知 embedding 模型不同仍要比，需顯式開啟並在報告中記下兩邊的模型與維度）；重跑 2 個 embedding 模型（bge-m3@1024、gemini@1024）× 4 個檢索模式（vector / vector+rerank / hybrid / hybrid+rerank）× 2 個題組（drcd / handwritten）共 16 次評測，產出新的 baseline 並提交。對齊 docs/plan/13 §4.2 W1 未做項③。"

## 背景（為什麼需要這個 Feature）

W1 把 embedding 從雲端模型換成地端模型，同時把向量維度由 1536 改為 1024。這是整個檢索
鏈上**影響面最大的一次單一變更**，而它在結案時明確記著一項未做：沒有跑評測，「換完之後
檢索品質如何」目前**沒有任何數字**。

問題不只是「還沒跑」。既有的量尺**刻意拒絕**回答這個問題——它比對兩份報告時會檢查
embedding 模型是否相同，不同就拒絕相減。那道防線擋的是「有人不小心換了模型還把兩個數字
拿來比」，而現在的需求正好是「明知模型不同、就是要比」。**這條路徑目前不存在**，不是被
關掉而是從來沒有。

同時暴露出一個更安靜的洞：報告記下了模型名稱，卻沒有記維度。W1 之後同一個雲端模型可以在
1024 維下跑（它支援維度截斷），於是「1536 維的舊報告」與「1024 維的新報告」會被判定為
同一把尺、順利相減，而它們量的不是同一件事。**這種錯誤不會有錯誤訊息**。

第三件事是解析度。用來量進步的那份手寫題組只有 24 題，每題值 4.2%——兩題翻盤就能造出
看起來顯著的差異。要用它來裁決「換模型是好是壞」，它太鈍了。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 拿到「換模型之後品質是好是壞」的判決 (Priority: P1)

維護者想知道地端模型換上去之後，檢索品質相對於原本的雲端模型是進步、退步還是持平；
兩份題組、四個檢索模式各自的結論是什麼；以及如果退步，退在哪幾題上。他打開評測說明
文件就能看到一張對照表，並且能追到每一格背後的那份報告。

**Why this priority**: 這是整包存在的理由。其餘兩個故事都是為了讓這張表可信而做的前置。

**Independent Test**: 在兩個模型都跑完之後，對同一題組、同一模式的兩份報告做比較，能得到
一組帶正負號的指標差值，以及依「主指標上升且次指標不退步」規則得出的勝負判定。

**Acceptance Scenarios**:

1. **Given** 兩份報告題組與語料相同、embedding 模型不同，**When** 未顯式開啟跨模型比較而
   要求比較，**Then** 系統拒絕比較並說明是哪一個欄位不同，不輸出任何差值。
2. **Given** 同上兩份報告，**When** 顯式開啟跨模型比較，**Then** 系統輸出各指標差值與勝負
   判定，且輸出中同時標示兩邊的 embedding 供應商、模型名稱與維度。
3. **Given** 兩份報告的題組或語料指紋不同，**When** 顯式開啟跨模型比較，**Then** 系統仍然
   拒絕比較——跨模型旗標只放寬「模型與維度」這一項，不放寬題組與語料。
4. **Given** 16 次評測全部完成，**When** 維護者閱讀評測說明文件，**Then** 文件中有一張
   2 模型 × 4 模式 × 2 題組的對照表，每一格可追溯到一份已提交的報告檔。

---

### User Story 2 - 不會被兩個看起來可比、其實不可比的數字騙 (Priority: P2)

維護者半年後翻出兩份報告想比較。他不記得當時的環境。系統必須替他判斷這兩份數據是不是
同一把尺量出來的，而不是把判斷責任丟回給他的記憶。

**Why this priority**: 沒有這一層，Story 1 產出的那張表在下一次有人換模型或換維度時就會
悄悄地錯掉——而錯的方式是「數字看起來完全正常」。這是量尺本身的可信度。

**Independent Test**: 可獨立驗證，不需要跑任何真實評測：以兩份人造報告（只有 embedding
維度不同、模型相同）要求比較，系統必須拒絕。

**Acceptance Scenarios**:

1. **Given** 一份新產出的報告，**When** 檢視它的內容，**Then** 其中記有 embedding 的
   供應商、模型名稱**與維度**。
2. **Given** 兩份報告模型名稱相同但維度不同，**When** 要求比較（未開跨模型旗標），
   **Then** 系統拒絕比較並指出維度不同。
3. **Given** 一份缺少維度欄位的舊報告，**When** 要求拿它與新報告比較，**Then** 系統拒絕
   比較，而不是把缺漏當成「維度相同」。
4. **Given** 任一種帶 rerank 的模式，**When** 產出報告，**Then** 報告仍必須記下 rerank 的
   供應商與模型（既有規則不因本次變更而鬆動）。

---

### User Story 3 - 量進步的那把尺解析度足夠 (Priority: P3)

維護者要用手寫題組裁決「換模型是好是壞」。24 題的題組裡兩題翻盤就是 8.3 個百分點，
那個幅度看起來像結論，實際上在雜訊裡。他需要一把每題權重更小的尺。

**Why this priority**: 它決定 Story 1 的結論可不可以拿來做決定。但即使題數不變，Story 1
仍然產得出對照表（只是結論的可信度較低），因此排在後面。

**Independent Test**: 可獨立驗證，不需要跑任何真實評測：載入題組並檢查題數、跨語言題數、
題目識別碼唯一性，以及每題的正解段落確實存在於凍結語料中。

**Acceptance Scenarios**:

1. **Given** 擴充後的手寫題組，**When** 載入並驗證，**Then** 題數不少於 50，單題權重不
   超過 2%。
2. **Given** 擴充後的手寫題組，**When** 檢查語言分布，**Then** 英文問句配中文段落的跨語言
   題不少於 3 題（維持既有下限）。
3. **Given** 擴充後的手寫題組，**When** 檢查每一題的正解，**Then** 每個正解段落識別碼都能
   在凍結語料中找到對應段落。
4. **Given** 題組已擴充（指紋改變），**When** 拿擴充前的舊報告與擴充後的新報告比較，
   **Then** 系統拒絕比較。

---

### Edge Cases

- **語料還在、向量被清空**：W1 的 migration 清空了所有向量，包括評測知識庫的。重跑評測時
  系統看到「文件已存在」而段落數也對得上，必須仍然把缺少的向量補齊，而不是判定為「已灌過
  了」就直接開始檢索——後者的症狀是每一題都零分，而過程中不會有任何錯誤。
- **同一個評測知識庫裡兩個模型的向量並存**：兩個模型現在都是 1024 維，資料上塞得進同一
  個欄位。檢索時必須明確地只用當次評測所指定的那個模型的向量，不得混用。
- **雲端模型在 1024 維下的行為**：該模型支援維度截斷，截斷後的向量與 1536 維的原始向量
  不是同一組數據。本次產出的雲端模型報告是 1024 維的，與 W1 之前的 1536 維報告**不可比**，
  這件事必須在文件與報告中留下痕跡，而不是靠記憶。
- **假供應商跑評測**：既有的兩道守門（embedding 是假的、或 rerank 模式而 reranker 是假的
  時擋下）必須在兩個模型下都仍然生效；本次新增的跨模型旗標不得成為繞過它們的路。
- **只跑到一半**：16 次評測是逐次執行的，中途失敗時已產出的報告仍然有效，重跑不得因為
  「已經有報告了」而拒絕，也不得產生重複的語料。
- **舊的 1536 維報告怎麼辦**：它們是 2B 系列結論的證據，不可刪除；但必須明確標示為歷史
  數據且不可與本次之後的任何報告比較。

## Requirements *(mandatory)*

### Functional Requirements

**題組（Story 3）**

- **FR-001**: 手寫題組 MUST 擴充至不少於 50 題，其中英文問句配中文段落的跨語言題不少於
  3 題。
- **FR-002**: 新增的題目 MUST 由人手撰寫，不得由語言模型從語料段落生成。理由是既有定案
  （docs/plan/13 §4「2B-0 結案」）：生成的問句會沿用段落原文字詞，天然偏袒字面檢索，而
  題組要回答的正是與字面檢索有關的問題。
- **FR-003**: 每一題的正解段落識別碼 MUST 存在於凍結語料中；題目識別碼 MUST 唯一。
- **FR-004**: 題組的守門測試 MUST 更新至新的下限，使「題數退回 24」會讓測試變紅。
- **FR-005**: 凍結語料 MUST NOT 因本次變更而重新取樣（語料指紋不變）。

**報告與可比性（Story 2）**

- **FR-006**: 每一份評測報告 MUST 記錄 embedding 的維度，與既有的供應商、模型名稱並列。
- **FR-007**: 兩份報告的可比性判斷 MUST 納入 embedding 維度；維度不同時預設拒絕比較。
- **FR-008**: 缺少維度欄位的報告 MUST 被視為不可比，而非視為維度相同。
- **FR-009**: 帶 rerank 的模式 MUST 繼續強制記錄 rerank 的供應商與模型（既有規則不變）。

**跨模型比較（Story 1）**

- **FR-010**: 系統 MUST 提供一條顯式開啟的跨模型比較路徑；預設行為維持拒絕。
- **FR-011**: 跨模型比較的輸出 MUST 同時標示兩邊的 embedding 供應商、模型名稱與維度。
- **FR-012**: 跨模型比較 MUST 仍要求題組指紋與語料指紋相同；該旗標只放寬模型與維度。
- **FR-013**: 勝負判定 MUST 沿用既有規則——主指標上升**且**次指標不退步。

**實測與產出（Story 1）**

- **FR-014**: MUST 完成 2 個 embedding 模型 × 4 個檢索模式 × 2 份題組，共 16 次評測，
  每一次都在真實的 embedding 服務與真實的 reranker 上執行。
- **FR-015**: 16 份報告 MUST 各自完整記錄當次的檢索參數、模型資訊與維度，並可由檔名指認
  出模型、模式與題組。
- **FR-016**: 新的對照組報告 MUST 進版控；既有的 1536 維報告 MUST 保留並標示為歷史數據。
- **FR-017**: 評測流程 MUST NOT 被接入自動化測試套件、lint、smoke 或 CI（既有界線不變，
  守門測試必須維持有效）。

**文件同步**

- **FR-018**: 評測說明文件 MUST 更新為：新的對照表（兩個模型 × 四個模式 × 兩份題組）、
  題組擴充後的新下限與已知限制、以及舊報告的歷史地位。
- **FR-019**: 開發 Roadmap 的 W1 未做項③ MUST 依實測結果結案，並記下判定結論。

### Key Entities

- **題組（Golden Set）**：一組固定的問句與其正解段落。屬性：題目識別碼、問句、問句語言、
  正解段落識別碼、整份的內容指紋。手寫題組與公開題組各一份，職責不同——手寫題組是量進步
  的尺，公開題組是迴歸護欄。
- **語料（Corpus）**：一份凍結的段落集合，含正解段落與干擾段落。屬性：段落識別碼、標題、
  原文、整份的內容指紋。本次不變動。
- **評測報告（Report）**：一次評測的完整結果。屬性：檢索模式、產出時間、題組與語料指紋、
  題數與段落數、**embedding 供應商／模型／維度**、rerank 供應商／模型（若有）、各項指標、
  逐題結果。
- **比較結果（Comparison）**：兩份報告的差異。屬性：主指標與次指標的兩邊數值、各指標差值、
  勝負判定、**兩邊的模型與維度標示**、是否為跨模型比較。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 維護者打開評測說明文件，能在一分鐘內找到「地端模型 vs 雲端模型」在 2 份題組
  × 4 個檢索模式下的完整對照表，共 8 組對照、每組含主指標與次指標的兩邊數值與差值。
- **SC-002**: 對 embedding 模型不同的兩份報告要求比較，在未顯式開啟跨模型比較時，100% 得到
  明確的拒絕訊息而非任何數字。
- **SC-003**: 對 embedding 模型相同但維度不同的兩份報告要求比較，在未顯式開啟時 100% 得到
  明確的拒絕訊息。
- **SC-004**: 手寫題組題數不少於 50，單題對主指標的影響不超過 2 個百分點。
- **SC-005**: 16 份報告中的任何一份，都能在不查閱外部紀錄的情況下指認出它的 embedding
  供應商、模型、維度，以及（帶 rerank 時）reranker 的供應商與模型。
- **SC-006**: 評測相關的執行路徑在自動化測試套件、lint、smoke 與 CI 中的出現次數為零，
  且既有的守門測試維持綠燈。
- **SC-007**: 本 Feature 完成後，開發 Roadmap 中「換 embedding 模型後沒有品質數字」這項
  未結事項降為零。

## Assumptions

- **本 Feature 只產出數字與判定，不含「要不要換回去」的決定**。若實測顯示地端模型顯著
  劣於雲端模型，本包的產出是那個結論本身；是否回退、是否改用其他模型，是依據這份數據
  再做的另一個決定，不在本範圍內。
- 評測租戶已存在且處於可用狀態，不由本 Feature 建立。
- 開發機的地端 embedding 服務與地端 reranker 服務可用（兩者都需要 GPU），且雲端模型的
  金鑰可用。**16 次評測必須在同一台機器、可行的話在同一段時間內完成**，否則「兩個模型的
  差異」會混進環境差異。
- 雲端模型在維度截斷後會自動正規化，因此 1024 維下的向量可直接用於既有的相似度計算，
  不需要額外的正規化步驟。此假設在實測第一份報告時即可證實或推翻。
- 凍結語料不變動，因此語料指紋在本次前後相同；只有手寫題組的指紋會改變。
- 既有的四個檢索模式定義、主次指標定義與勝負判定規則均不變更。
- 擴充題組所需的段落全部來自既有的凍結語料，不引入新的文件來源。

## Dependencies

- 依賴 W1 已完成（向量欄位已為 1024 維、地端 embedding 服務已可用）。
- 依賴 2B-0 建立的評測基礎設施（題組與語料格式、指標定義、報告格式、比較規則）。
- 依賴 2B-4 建立的地端 reranker 服務（四個模式中有兩個需要它）。

## Out of Scope

- 切塊策略的評測（屬另一個工作包）。
- 擴充公開題組或重新取樣任何語料。
- 新增第三個 embedding 模型或新的檢索模式。
- 把評測接進 CI 或任何自動化流程。
- 依據結論調整任何檢索參數的預設值。
